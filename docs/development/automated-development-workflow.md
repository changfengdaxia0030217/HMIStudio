# HMIStudio 自动开发与验证流程

> 适用分支：`feature/**`；当前工作分支：`feature/m0-core-contracts`

## 目标

以“仓库修改—自动构建—检查日志—修复—再次验证”的循环推进 HMIStudio，尽量减少开发者手动复制终端命令和错误输出的次数。

## 标准循环

1. **检查现状**：读取目标分支的代码、接口、测试和最近提交，先确认现有实现，不凭猜测重写。
2. **小步修改**：围绕一个明确功能修改文件，补充或更新自动化测试；避免把未验证的大量改动一次性混入。
3. **提交到功能分支**：通过 GitHub 仓库连接提交改动，保留清晰的提交说明。
4. **自动触发 GitHub Actions**：工作流在推送到 `main` 或 `feature/**` 时运行；针对 `main` 的 Pull Request 和手动触发仍然保留。
5. **检查真实结果**：读取对应提交的 Actions 运行状态、步骤结果和失败日志。不能把“已提交”或“已触发”误称为“测试通过”。
6. **修复并重试**：若构建或测试失败，分析日志、修复代码或测试，再提交并等待下一次自动运行。
7. **报告状态**：明确区分已提交、工作流已启动、构建通过、测试通过、运行时检查通过；注明尚未覆盖的风险。
8. **保持工作区同步**：GitHub 远端提交不会自动更新已打开的 Codespace 本地工作区。需要在 Codespace 中使用时，先确认本地改动已妥善保存，再拉取远端更新。

## 当前 CI 覆盖

`.github/workflows/dotnet.yml` 在 Windows runner 上执行：

- Node.js 20：安装依赖并构建 React/TypeScript 前端。
- .NET 10：还原依赖、Release 编译、自动化测试。
- 运行时 API 冒烟测试：启动服务，检查健康接口、变量读写、演示画面绑定、画面保存以及重启后的持久化。
- 报警端到端检查：通过变量写入触发报警、确认报警、恢复报警，检查活动报警状态与确认时间，并在服务重启后验证 SQLite 报警历史仍然存在。

报警引擎单元测试覆盖触发/恢复、重复更新不重复触发、确认时间、活动报警恢复和 SQLite 历史跨管理器重启保留。每个新功能还应增加相应的自动化测试；既有冒烟测试通过并不代表尚未实现的功能已经得到验证。

## 当前能力边界

- 助手可通过 GitHub 连接读取、创建和更新仓库文件，并读取可访问的 CI 运行结果与日志。
- GitHub Actions 在远程 runner 中执行构建和测试，不等同于助手直接控制用户的 VS Code / Codespace 终端。
- 当前连接没有直接在用户 Codespace 中执行任意 shell 命令或操作本地工作区的能力。
- 因此优先用远程 CI 自动验证，尽可能避免用户复制粘贴命令与日志；若必须进行仅能在用户 Codespace 或本机完成的操作，再说明原因并请求最少的协助。
- 绝不声称执行了实际未运行的命令，也不把推测结果当成测试证据。

## 功能完成标准

- 代码已提交到预期分支。
- 对应提交的 CI 已完成，而不只是已排队。
- 前端构建、.NET 编译、自动化测试和相关运行时检查均通过；若某项不适用或未执行，应明确注明。
- 新功能的关键成功、失败、边界和持久化行为有自动化测试覆盖。
- 对失败结果已修复并重新验证，或明确记录阻塞原因。
